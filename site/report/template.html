Scope, research questions and hypotheses

The evaluation asks whether OptimusDB, the decentralised data layer of Swarmchestrate, can serve orchestration metadata across edge, fog and cloud as well as established decentralised data stores.

Research questions

RQQuestionExperiments
RQ1What does running OptimusDB cost on resource-constrained edge nodes, compared with other decentralised stores?E4
RQ2How do its latency, throughput and query capability compare under orchestration-style workloads?E1, E2, E3
RQ3Does it remain available during network partitions, and does it converge without losing acknowledged writes?E5

Baselines and why they were chosen

All five baselines are decentralised data stores that replicate without a central coordinator, which is the property OptimusDB must offer to a swarm of orchestration agents. They span the design space: a CRDT-replicated SQL database (Corrosion), two JavaScript peer-to-peer stores (Gun.js; Autobase with Hyperbee), a range-reconciled document store (Iroh docs) and a distributed hash table (OpenDHT). Centralised or leader-based databases are excluded on purpose: they solve a different problem.

What a quick run is for

Quick mode runs every scenario once on 10⁴ records with short windows, in about 80 minutes. It verifies the whole pipeline (deployment, preload, replication checks, load generation, result files, analysis) and gives a first look at each comparison. Verdicts on a quick run are computed exactly as on the campaign, but are labelled indicative. The method chapter lists every difference from the campaign.

{n}.3 Parity between systems

A comparison is only meaningful if each system is configured sensibly and asked to do the same work. The measures below were taken for that reason; each is recorded with the results.

  • Same result. Every operation returns the whole documents and the client decodes them, on every system. Until quick run 3, Corrosion's WO query returned only the ids of matching rows while the other systems returned the documents; this was corrected before quick run 4.
  • Durability. Corrosion runs SQLite in WAL mode with synchronous = NORMAL (no flush per commit). OptimusDB runs with the equivalent setting: IPFS blocks and the store-head cache are written without an fsync per write. The other baselines run with their defaults.
  • Indexes. OptimusDB indexes type, status, region, resource_id; Corrosion's schema and OptimusDB's SQLite tables get the same secondary indexes, so no system has an index advantage in E3.
  • Runtime limits. The Go 1.19 build of OptimusDB does not read cgroup limits, so GOMAXPROCS and GOMEMLIMIT are set to the container's limits; the Rust and Node.js runtimes of the baselines read them themselves.
  • Diagnostics off. OptimusDB's provenance annotations, metadata enrichment, semantic index and log shipping are off; no baseline has an equivalent. Logging is at warning level for OptimusDB, Corrosion and Iroh.
  • Baseline configuration. Each baseline runs in the configuration that serves it best and was calibrated where it failed at low load: Autobase uses three indexers (eight caused 13–27 % timeouts), Gun.js uses a flat schema (the original wrapper leaked about 9 MB per query).

Keys follow a scrambled Zipfian distribution (θ = 0.99). The WO query asks for resources in one region with status Running, which matches about 1/16 of the records (about 640 documents at 10⁴). Records are JSON resource descriptors padded to 2 KB; region, CPU, memory and status take independent base-4 digits of the record number, so query predicates are uncorrelated and expected row counts are exact.

The load generator is open loop: operations are issued on a Poisson schedule whether or not earlier ones have finished, and latency is measured from the scheduled start, so a slow system cannot hide queueing delay. The per-operation timeout is 10 s; at most 2,000 operations may be in flight.

{n}.7 Verdict rules

  • Saturation (E2) is the highest offered load at which a system achieves ≥ 90 % of the operations it supports with < 1 % errors. A system that does not keep up even at the lowest load counts as 0 ops/s in the baselines' median.
  • Unsupported operations (OpenDHT cannot enumerate data) are excluded from errors and reported separately; OpenDHT's throughput target is 90 % of the operations it supports.
  • Correctness (E3) means the answer has exactly the expected number of rows; latency is only compared for correct answers.
  • Lost write (E5): an acknowledged key whose final value is missing, or older than a write that provably came after it on the same side of the partition. A concurrent write may legitimately win.
  • Statistics (campaign only): run-level values; Mann–Whitney with Holm correction; Cliff's δ; 95 % confidence intervals.

Threats to validity

What could make results of this testbed wrong or not general, and how each is handled. The observations found in this particular run are listed in the integrity chapter.

ThreatWhy it mattersHandling
Few repetitionsWithout repetitions there is no variance estimate; one slow period of the machine can move a whole system's numbers.Campaign: 5–10 repetitions; blocks shuffled with a fixed seed; the start time of every run is recorded.
Short windowsP99.9 needs thousands of operations; with 1,500 it rests on one or two samples.Campaign: 300 s windows (about 15,000 operations per E1 run) and 300 s per E4 level.
Client saturationA load generator that falls behind makes every system look slow.Generator CPU, issue delay and node CPU recorded per run; client-limited steps are not counted against a system; the generator runs in several processes (busiest one checked).
Host contentionThe testbed's limits (about 11.5 CPUs) nearly fill a 12-CPU Docker VM.Give the VM more CPUs where possible and keep the PC otherwise idle; the client-limit check exposes contention.
Incomplete preloadA system measured before its data reached every host is measured on a partly replicated store.The harness waits for a sample of keys on every host (up to 900 s in the campaign) and marks runs that time out.
Unequal workSystems must be asked for the same result.Every operation returns and decodes whole documents on every system; checked by a test.
Interface costCorrosion's answer format costs the client more to decode (each document is a JSON string inside an NDJSON row).Kept, as it is what a client experiences; disclosed.
EmulationOne machine, cgroup limits and netem stand in for real edge devices and links.Stated in the paper; link values from Table 7; edge limits match a Raspberry Pi 4 class device.
Wrapper effectsGun.js, Autobase and Iroh are libraries reached through small HTTP wrappers.Wrappers calibrated on a single node and in the cluster; a failure on an unsaturated single node is treated as a benchmark defect and fixed first.
Configuration biasOptimusDB settings were tuned from profiles.Every setting is logged per run and listed in the paper; each has a counterpart in a baseline (durability, indexes) or is a documented default of the component.

Benchmark

  • Corrosion's WO query fetches the documents, not only their ids; reads on the wrapper-based systems decode the document (before quick run 4).
  • Corrosion schema and OptimusDB SQLite tables have the same secondary indexes.
  • Gun.js wrapper uses a flat schema (memory leak in the original); Autobase uses three indexers; both wrappers survive failed requests.
  • E1: a run with > 20 % errors or a node that stopped answering is followed by a fresh deployment.
  • E2: a system that cannot keep up at the lowest load counts as 0 in the baselines' median.
  • OpenDHT: queries it cannot express are unsupported, not errors.
  • Load-generator validity check (generator CPU, issue delay, node CPU per run); Corrosion answers decoded in one call per response; an error event from Corrosion counts as an error.
  • Evaluation report generated from each run's files, with a copy saved when the run finishes.
  • After the first pilot at 10⁵ records: the load generator runs in several processes (same operations and scheduled times); the client's connections are renewed after a redeployment; the Gun.js, Autobase and Iroh wrappers evaluate WO queries without holding every document in memory, Gun.js reads its local replica, and Gun.js and Autobase run at most two scans at a time; OptimusDB pinned to commit 479504d. The H1 detail also states the comparison with the baselines that completed the whole WO mix (verdict unchanged).
Appendix B

Glossary

P50, P99, P99.9The latency below which 50 %, 99 % and 99.9 % of successful operations completed.
Tail ratioP99.9 ÷ P50; how much slower the slowest operations are than a typical one.
Open loopOperations are issued on a fixed schedule regardless of earlier ones finishing; latency counts from the scheduled time.
Issue delayTime between an operation's scheduled start and the moment the client actually sent it; near zero when the client keeps up.
SaturationHighest offered load achieved at ≥ 90 % with < 1 % errors.
BlockOne deployment and preload of one system; all its runs follow on that data in shuffled order (YCSB load and run phases).
LOCAL_THEN_REMOTE_MERGEOptimusDB strategy: answer from the local replica; ask peers only when it has no matching rows.
ConvergenceTime from healing a partition until all replicas have identical content hashes.
Censored valueA measurement stopped at a limit (e.g. 120 s): the true value is at least the limit.
CRDTConflict-free replicated data type: replicas accept writes independently and merge deterministically.
